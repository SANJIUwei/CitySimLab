# 2026-09-12 GPU 寻路内核 Benchmark

## 本次结果

GPU 寻路内核已经独立跑通，当前实测环境：

- GPU：NVIDIA GeForce RTX 3060 Laptop GPU
- 工作量：2000 次寻路
- 结果：2000 次全部找到路径，`cost` 与预期一致
- 总耗时：1.946 s
  - Upload：80 ms
  - Dispatch：10 ms
  - Readback：1856 ms

按总耗时计算，当前瓶颈非常明确：

- Upload：约 4.1%
- Dispatch：约 0.5%
- Readback：约 95.4%

因此当前 GPU 路径搜索虽然已经完成了正确性验证，但端到端性能并不优于现有 CPU 并行方案。瓶颈不在 GPU 内核本身，而主要出现在 GPU → CPU 的结果回读阶段。

## 实现规律

### 1. 批量提交是前提

GPU 版本不能把一次寻路当成一次独立的小任务频繁提交。当前采用批量提交，将多个寻路请求组织成一个计算批次，才能获得 GPU 并行计算的意义。

### 2. CSR 矩阵适合当前路网数据

将路网邻接数据整理为 CSR（Compressed Sparse Row）结构，可以用较紧凑、连续的数据布局提供 GPU 内核所需的邻接访问方式，避免直接搬运高层 C# 容器结构。

### 3. SPFA 在当前内核里优于 Bellman-Ford

当前实验中，SPFA 比 Bellman-Ford 更快。主要观察不是“SPFA 在所有 GPU 图算法中都更好”，而是当前路径搜索的工作特征下，Bellman-Ford 的大量无效松弛迭代带来了更高计算量，而 GPU 线程间同步与通信成本又不低，因此 SPFA 的实际表现更好。

这个结论只作为当前实验结果，不应直接推广成通用 GPU 最短路结论。

### 4. 显存/主存拷贝才是主要成本

当前总耗时中 readback 占约 95.4%，说明“GPU 算得快”并不等于“整个寻路请求返回得快”。如果每个批次都需要把大量结果完整拉回 CPU，那么 GPU 的计算优势很容易被数据传输抵消。

## 与 CitySimLab 调度器的关系

当前 GPU 内核已经验证了“批量寻路 → GPU 计算 → 返回结果”这条技术路线，但还不代表 `ComputeScheduler` 的 GPU Backend 已经完成接入。

现阶段更重要的结论是：

> GPU Backend 应把“批量计算能力”和“结果返回成本”同时纳入调度考量，而不能只比较 Compute Shader 内核的执行时间。

对于模拟游戏，最终评价 GPU 寻路应看完整的端到端成本，以及它对每帧 Rendering + Simulation 总预算的影响，而不是只看 Dispatch 时间。

## 后续优化方向

1. **内核融合**：尽量减少 GPU 计算阶段之间的往返与中间结果落地。
2. **共享内存**：对高频访问的局部数据进行更快的片上缓存，降低全局显存访问压力。
3. **异步回传**：避免主线程同步等待 readback，让计算与后续模拟工作重叠。
4. **动态批大小**：根据当前待处理请求数量与 GPU/帧预算动态决定一次提交多少寻路任务。
5. **端到端 Benchmark**：后续不能只记录 upload / dispatch / readback，还需要加入 GPU rendering time、总 frame time、FPS、寻路延迟与吞吐量，判断 GPU 寻路是否值得占用渲染资源。

## 当前判断

GPU 寻路内核已经从“可行性假设”进入“可运行、可测量”的阶段。当前数据说明：

```text
GPU Compute 很快
        ↓
但 Readback 很慢
        ↓
端到端寻路仍然受传输拖累
```

因此下一阶段重点不是继续单纯追求更快的寻路内核，而是围绕“少传输、少同步、批量化、异步化”优化整个计算管线。
