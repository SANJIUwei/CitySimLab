# 架构

纯 C# 模拟内核。Core 不引用 Unity。

全局图只保存道路。建筑不进全局图，挂接缓存包含 `segment + t` 与允许进出方向。

## 仓库模块

| 模块 | 负责 | 不负责 |
|---|---|---|
| `CitySim.Core` | 规则、数据、计算合同 | 画面、Unity |
| `CitySim.Headless` | 命令行观察 | 规则本身 |
| `CitySim.UnityMock` | 少量生命周期概念 | 真实引擎 |
| `CitySim.Tests` | 验证规则 | 玩法设计 |

Core 目录：

```text
World/      WorldPosition
Roads/      Node、Segment、Lane、Network、Building
Routing/    PathCenter、Trip、TripStarter、LocalApproach
Compute/    Scheduler、Job 合同、CPU/GPU Backend
Movement/   Thing
```

全部在 `namespace CitySim.Core`。

## 稳定接口

| 概念 | 作用 |
|---|---|
| `RouteEnd` | 路上的一端：`RoadAttachment` + 进出点 |
| `TripCommand` | 一次出行请求 |
| `Trip` / `GlobalPath` | 路线结果 |
| `IComputeCenter` | 业务中心自己排队，调度器来取作业 |
| `IComputeJob` | `Execute` 计算，`Apply` 回写 |
| `IComputeBackend` | 怎么算。当前默认 `CpuParallelBackend` |

寻路算法落在 solver / `FindPath`，不由 `Thing` 或 `Building` 决定。

## 依赖

```text
TripStarter / Building / Thing
    ↓
PathCenter
    ↓
ComputeScheduler
    ↓
IComputeBackend
```

`PathSearchJob` 调用 `RoadNetwork.PlanTrip`。`Building` 不依赖调度器。`Thing` 不创建线程。

`RoadNetwork` 保存路段、邻接关系和路口连接，`PlanTrip` 以两端的接入条件调用合法路径搜索。

## 一次出行

```text
Building / 路上的点
    ↓
RouteEnd
    ↓
TripStarter.Request
    ↓
PathCenter.Enqueue
    ↓
ComputeScheduler.Tick
    ↓
PathSearchJob.Execute → RoadNetwork.PlanTrip
    ↓
Apply → Thing.ReceiveRoute
    ↓
Thing.Advance（跳逻辑点）
```

同一段仅在方向和出入口都允许时直达；否则尝试合法绕行。跨段会综合比较合法的起终端点和转向，不直接取最近的路口。

## WorldPosition

坐标和直线距离。`WorldPosition.Distance`。

不负责路网、出行、调度。

## RoadNetwork

保存 Node、Segment，以及 Node 之间的邻接表 `_adj`。提供 `FindPath`、`PlanTrip`。

### 负责

- 路口、路段、车道数据
- 全局 ALT 和 Dijkstra，状态包含来向车道；路线代价由登记路段权重、接入路段比例和转向附加成本组成
- 把两端 `RouteEnd` 拼成 `Trip`

### 不负责

- 排队、线程、GPU
- 建筑生命周期
- `Thing` 怎么走

### 现状

双向邻接表是 ALT 的放松图，只作为下界；合法查询按实际车道方向、车型、查询时段与路口连接走。无显式车道配置的普通路段采用双向车道样式；清空已配置的车道不会重新变成双向。换道和每帧交叉口冲突尚不模拟。

`Length` 是几何长度。`Cost` 是图权重。两套数。

## Building

车行开口（旧地图可用楼门）投影到符合配置的路段，缓存 `RoadAttachment`，含 `segment + t` 和进出方向。

### 负责

- `AttachNearest(network, maxDistance = +∞)`：超过最大距离不挂，`Attachment` 为 null
- `AttachTo(segment, t)`：手工选择也要满足路段的开口、层级、间距和分隔条件；自动寻找还受最大距离与接入优先级约束

### 不负责

- 发起出行（那是 `TripStarter`）
- 寻路、走路

未接入的楼不能出行。没有路、或最近路太远，都是没挂上。

不切段、不加空间索引。`AttachNearest` 仍扫全部路段。

## PathCenter

寻路请求队列。实现 `IComputeCenter`。

### 负责

- `Enqueue` 收请求
- `Dispatch` 把作业交给调度器
- `Process` 向调度器要本 Category 的预算

### 不负责

- 最短路算法
- 计算预算怎么分
- 在 CPU 还是 GPU 上算

`Pathfinder` 是旧名，转到 `PathCenter`。点对点 `Request` 也进同一队列。

`PathSearchJob` / `NodeSearchJob` 不属于建筑或载具。当前 `PathSearchJob.Apply` 仍直接写 `Thing`。

## ComputeScheduler

计算任务的排队和顺序。

### 负责

- 优先级（0–100 分，11 个桶）
- 虚拟运行时间，低优先级不会饿死
- `Tick` 时先让中心 `Dispatch`，再把批次交给 Backend
- 主线程只 `Apply`

### 不负责

- 路径规则、Traffic、建筑
- 决定算法（Dijkstra / A* / GPU kernel）
- 默认不拥有 GPU 后端

默认 Backend 是 `CpuParallelBackend`。`GpuDeferredBackend` 存在且 `Available = false`，不挂在调度器上。

## Thing

收到 `Trip` 后拼步骤表。`Advance()` 一次跳一个逻辑点。

`Thing.Advance` 保留用于逻辑步骤；`TimedRoadTraveler` 可按时间、显式地图单位换算和车道限速推进，经过路口时检查实时相位、开口及路段限制。无信号路权评估必须由调用方提供明确的冲突信息；当前没有整城节拍或自动检测全部车流冲突。两种游标遇拓扑变更都会停止推进、等待重规划。

## 计算分层

```text
业务请求（出行、以后别的 Category）
    ↓
IComputeCenter（自己排队）
    ↓
ComputeScheduler（预算和顺序）
    ↓
IComputeBackend（怎么算）
    ↓
Job.Apply（回写结果）
```

业务对象不创建线程、不 Dispatch GPU。

## 扩展时不该改谁

| 未来变化 | 应改 | 不该改 |
|---|---|---|
| 第二种寻路算法 | `RoadNetwork.FindPath` 或独立 solver | `Thing`、`Building` |
| GPU 寻路进仓库 | 新 Backend + 批处理合同 | Scheduler 的排队规则、玩法对象 |
| 按距离移动 | `Thing` / 将来的 clock | `PathCenter`、图结构 |
| 单行路 | 车道方向及路口/开口连接 | 建筑挂接点的几何格式 `segment + t` |
